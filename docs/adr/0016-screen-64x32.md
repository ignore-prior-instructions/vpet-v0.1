# 0016: 64x32 screen, 32x32 pets, 12x12 icons, 5x7 font

Status: accepted (supersedes 0012)
Date: 2026-09-21

## Context

[ADR 0012](0012-screen-32x16-and-cell-sizes.md) chose 32x16 because the 128x64 SSD1306 is
exactly that at 4x. Playing the published web build showed the cost: 8x8 menu icons are not
recognisable (a bowl, a broom and a diamond are the same blob at that size), the selected icon
is only an inverted square, and a 3x5 font can label nothing but the status pages. The same
OLED is exactly 64x32 at 2x, which still reads as chunky one-bit handheld pixels.

## Decision

The screen is 64x32, one bit per pixel, 8 bytes per row, 256 bytes per frame. Pets are 32x32
cells, bottom-anchored. Menu icons are 12x12 (art inside 11x11; row 11 and column 11 blank).
Items and effects are 16x16. Status hearts are 14x14. The font is 5x7 with a 6 px advance and
gains a space glyph. Egg, tombstone are 32x32; splash screens 64x32.

The menu is two rows of four icons with the selected icon inverted and its name drawn in 5x7
on the bottom rows: the screen tells you what you are about to do.

Every sprite was redrawn at the new size rather than upscaled (the extra pixels are for detail,
not for bigger blocks). The frame format change bumps `ABI_VERSION` to 2. The save format is
untouched: nothing persisted depends on screen geometry.

## Consequences

- The OLED is filled exactly with 2x2 blocks; the browser scales by CSS as before.
- Frames are 4x larger (256 B): still trivial for I2C at 4 fps and for parity diffs.
- Sprite bytes grow ~4x (a species ~6 KB); `vpet.wasm` stays well under the 64 KB gate.
- Every golden's frame block changes; their inspect blocks do not. The hosts' only change is
  a constant (64x32 canvas, 256-byte frame, ABI v2).
- Validator thresholds that are pixel counts (component size, checkerboards, bbox bands)
  scale; ratios (density, symmetry, eye fraction) do not.
